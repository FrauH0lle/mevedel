    Project backlog¶

    Canonical home for concise future-work requests and unresolved defects. Detailed plans, investigations, and review reports belong in work://shared/. Read this before planning work in any listed area.

    Use the inbox for ideas that have not been investigated yet. Promote an item to a detailed entry when its scope and current status are understood. Remove items when they are implemented, obsolete, or no longer valuable.

    Execution¶

    Harness-enforced Bash timeouts¶

    Managed Bash commands run until they exit or are stopped. 145c66a removed mevedel-bash-timeout (120 s default) and the model-facing timeout_seconds, so only a native timeout the model writes itself bounds a command. A forgotten command keeps running and holds the system sleep inhibitor. When Bash completion wake-ups and the Monitor tool were added (2026-10), the user decided against restoring a Bash deadline for now; only Monitor expires (timeout_ms). Revisit if forgotten commands become a problem in practice. Reference point: Claude Code caps background commands at 10 minutes by default and 2 hours at most. Expiry would reuse the existing TERM/KILL process-group teardown and report a timeout outcome.

    View¶

    Pinned prompt on the remaining surfaces¶

    The main view and agent transcript views pin the governing prompt on its own header row below the status strip (view contract). Two surfaces still lose the prompt once it scrolls away:

    • Directive frames set a window-level header-line-format to their condensed directive header (mevedel-directive-frame--ensure), which hides the buffer's prompt row. Decide whether the narrow frame should spend a second row on it, or show the prompt only while its header is off screen.
    • The browser viewer (relay/viewer/) has no pinned prompt. A sticky element above the transcript, fed from the rendered prompt headers, is the analogue; check it on the narrow-phone viewer.

    Whiteboard¶

    Excalidraw parity left out of the element model¶

    ADR 0121 stores and draws Excalidraw elements but cherry-picks interaction. Not yet implemented: segment dragging for elbow arrows, object and grid snapping, a frame tool and moving children with their frame, sticky-note font auto-fit with its lifted corner and date footer, the constant-width laser-pointer stroke, and embedding the scene in PNG/SVG downloads. Add each when a board needs it; Excalidraw's behavior is compiled in excali-mode's docs/excalidraw-spec.md (https://github.com/yibie/excali-mode).

    Review¶

    Automatic turn advisor¶

    Consider an opt-in second-model review of successful root turns, with bounded feedback delivered to the next request. Reuse the Stop hook, reviewer runtime, and reminder delivery. Keep findings distinct from Buddy's advisory notes, and specify evidence scope, deduplication, cooldown, cancellation, and cost before implementation. Pursue when recurring review failures justify the extra model call; keep it advisory, without restarting completed turns. Implement this bounded feature before considering generic prompt or agent hook handlers. There is no automatic root-turn reviewer/instruction-injection path today. The original request came from the 2026-08-20 watchdog/advisor discussion.

    Buddy comment trigger¶

    Follow-up to /buddy: a comment containing BUDDY! in a buffer with mevedel-buddy-mode runs guidance at once on its enclosing defun, using the comment text as the question. No existing watcher fits as is. Buddy's change recording sees the edit, but the trigger needs its own rules before it can use the idle timer:

    • Fire when the edit settles, not on the ! keystroke, so the question after the marker is complete.
    • Skip mevedel-buddy-min-interval and preempt an automatic review, as mevedel-buddy-guide does.
    • Fire once per comment. A comment left in the buffer must not fire again on later edits elsewhere. Key it in memory by marker or text hash.
    • Send the enclosing defun (beginning-of-defun), or the whole buffer when there is none.

    Detection checks only the changed lines in mevedel-buddy--after-change; it never polls or rescans buffers. Buddy does not remove the comment after the guidance runs: the user deletes it.

    Hook extensions¶

    Task transition events¶

    Consider a task transition event when notifications or tracker synchronization need to observe every completion. A hook matching TaskWrite misses automatic completion by mevedel-tool-task-finalize-owner in mevedel-tool-task.el. Observe actual state transitions across both paths rather than tool calls alone. Defer until a concrete integration needs that coverage.

    Deferred extensions¶

    • HTTP, prompt, MCP-tool, and agent handlers: revisit when a named workflow cannot be served adequately by command/Elisp handlers. Define permission, cancellation, and recursive-hook behavior before adding a handler type.
    • Handler-level predicates: keep conditions inside handlers unless repeated workflows or measured launch cost justify declarative filtering. Prefer an event-specific matcher where sufficient, such as skill-name matching for UserPromptExpansion, rather than a general predicate language.
    • Configuration, cwd/files, tool-batch, and shell-environment events: add individually when a caller needs a boundary existing events cannot express; define the event's scope and control effects before implementation.

    Plugins¶

    Opt-in update notifications¶

    Managed plugins are shallow GitHub clones (mevedel-plugins-install); they change only through /plugin update NAME (git pull --ff-only) or the cockpit's update action. Nothing tells the user an update exists. Automatic updates stay out of scope: they change executable code, and hooks, without consent.

    Shallow clones never refresh their remote refs, so any check needs the network. The current git seam (mevedel-plugins--process-git) is a synchronous process-file that would block Emacs, and the plugin modules have no async process, timer or place to surface results. Design:

    • mevedel-plugins-update-check-interval: nil (default, no checks) or a number of days. No network call at load or startup: the first check runs on an idle timer after the registry is first used in a session, and the last check time persists in global plugin state, so restarts within the interval do not check again.
    • The check runs git ls-remote origin HEAD asynchronously (make-process, one plugin at a time) for each managed root and compares the result with local HEAD. Results are cached per plugin.
    • Surfacing follows NO SURPRISES in CODING_STANDARDS.md: one echo-area message per newly seen upstream commit ("updates available for N plugins; /plugin to review"), never repeated for the same commit; cockpit rows show "update available" from the cache. Offline or failed checks stay silent apart from a "check failed" row note.
    • A cockpit "Check for updates" action runs the same async check on demand, regardless of the interval setting.
    • Scope: mevedel-plugin-lifecycle.el (async check), mevedel-plugin-registry.el (setting, cached state), mevedel-plugin-ui.el (row note, action), docs/skills.md; tests through an async git-executor seam, including the "no network at load" guarantee.

    Browser session history actions¶

    Owner links can create a Conversation Fork from a settled assistant response (fork frame, docs/collaboration.md). Rewind, edit and Worktree Fork remain Emacs-only. Each needs an owner-only typed frame that resolves the same stable forkPoint the projection already publishes, and runs the existing Emacs transaction. A browser frame runs under inhibit-interaction, so any native minibuffer or overlay confirmation would refuse it. Each action therefore needs a browser-side confirmation of its own.

    • Rewind: mevedel-session-rewind confirms in Emacs. It names both sides of the boundary, capture gaps, the files to restore, external changes it would overwrite, and the live state it would clear. A browser rewind needs a host-built impact card (a ui-request like plan approval, bounded, with an "open in Emacs" fallback when the impact does not fit) and an owner confirmation. Every room in the session must then republish its records after the truncation. Redo follows the same shape.
    • Edit: resubmitting an edited earlier prompt is Rewind before that prompt plus a new prompt, so it should follow Rewind and reuse its card.
    • Worktree Fork: needs Git preflight, branch naming (the Worktree plan acceptance already validates a browser branch name) and the retained-artifact error path.
    • Fork with a first prompt: the browser fork publishes an empty child and the owner writes in its room. Sending the prompt with the fork, as the f composer flow does, could reuse the new-session first-prompt path.
    • Non-owner request flow: a full-control guest could ask, like new-session, with the owner or host approving.

    View and transcript¶

    • Stale-zone scan cost (2026-10-18): mevedel-view-zone--delete-stale-text scans the whole buffer on every changed reconcile, including each per-second rail update. A synthetic transcript showed cost growing with size; no real long session was profiled. Profile one before narrowing the scan, and keep stale-text recovery across undo, reinsertion and lost local state.
    • Skill hint (2026-10-18): the hint refreshes only when the view's text changes, so a skill-list change waits for the next edit or render. Refreshing on skill changes would add per-command or push machinery; accept or close.
    • Ask overhaul timing failures (2026-10-18): full-suite timing failures in journal-recall-expiry and acp-turn-start/tool-hooks did not reproduce under 8 contention copies on one CPU (2026-10-31); only the original ordered conditions remain to try.
    • Browser completion notices and image-button acceptance limits (2026-10-18): renderer/host protocol checks did not include browser visual acceptance of the final completion notices. Image-button graphical checks verified activation and normal-state decoration suppression, not hover-theme or higher-priority overlay styling. Locate subsequent evidence or exercise those specific states before extending the historical acceptance claims; preserve image activation, committed-artifact resolution and notice ownership/wording.
    • Remaining layout checks (2026-10-17): minibuffer-active and graphical variable-height or wrapped tall drafts have no check; run them on the private-KWin runner, preserving draft position and interactive row identity.
    • Task-panel mouse disclosure (2026-10-16 suggestion): panels currently toggle with TAB/RET while mouse clicks place point. Consider a clickable header only, preserving selection on task rows. This is an optional consistency improvement, not an implemented feature or a request for per-task detail inspectors.
    • Pending-input local preview acceptance limits (2026-10-16): the implementation handoff reported rendered-consumer tests, but no separate read-only-authority, deferred-render, or live graphical interaction checks. This is historical verification scope, not a reproduced defect or proof current coverage is absent. Before claiming those scenarios verified, locate subsequent coverage or run a bounded check that preserves drafts, selection, viewport, delivery and queue management's explicit pause semantics.
    • Automatic Read collapse (2026-10-14): an opened Read row later appeared collapsed in a live session; replays did not reproduce it. A bounded fold trace was prepared; the next step is a consented live reproduction. The prior live trial used an unattended scratch view, which deferred rendering: its sampler never opened a row while busy, so the final no-anomaly render did not test mid-turn row survival. Use an attended view, actually open the row during the active turn, and attribute trace events to the relevant buffer and time.
    • Mailbox hierarchy (2026-10-14): a following Eval should be a sibling of the Finished card inside the same expanded activity. Later live inspection and incremental/canonical replays found it nested correctly, but did not reproduce the screenshot-time transition. The later collapsed-card display-boundary fix does not establish that transition's cause. Replay retained source/view-tail anchors and groupability across ToolCall metadata publication or targeted replacement; preserve incremental rendering rather than rerender every event. Under ADR 0119's rule, only a tool starts a run, so the Eval is a sibling of the Finished card only when a tool precedes the card in that run.
