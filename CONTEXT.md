# Context

This glossary captures the domain language for mevedel. Keep it focused on user-facing concepts and durable workflow terms, not implementation details.

## Product domain

- **mevedel** — An Emacs Lisp package for visual AI-assisted programming workflows inside Emacs.
- **workspace** — The project context mevedel operates in, including repository roots, workspace configuration, persistent memory, and session state.
- **resource locator** — The canonical identity of a selected resource shared by atomic bindings and resource resolution. It names a target, not its content, authority, or mention operation. _Avoid_: resource address, resource grant
- **resource address** — The context-qualified `scheme://` text form of a resource locator consumed by filesystem-shaped tools. It may be exact, session-relative, or a discovery query. _Avoid_: URL, mention, resource grant
- **execution target** — The single filesystem and command environment in which a session's workspace effects occur. It may be local, a remote host, or a container, and one session cannot address another target. _Avoid_: remote environment, execution host
- **target-native path** — A path as named inside an execution target, without a client-specific TRAMP prefix. Remote transcripts and tool arguments use target-native paths while navigation and authorization retain the session's execution target. _Avoid_: bare remote path
- **agent resource** — A portable user- or project-authored asset intended to be shared with agent tools, such as a skill, plugin, or durable memory.
- **mevedel state** — Runtime data owned by mevedel, such as session persistence, tool artifacts, input history, and generated metadata.
- **session** — A chat/workflow instance attached to a workspace. Sessions hold transcript state, permissions, reminders, tasks, agent state, and persistence metadata.
- **session lease** — Renewable exclusive authority for one client to mutate a durable session. Other clients may inspect its last published state, but may resume or change it only after acquiring the lease.
- **portable project authority** — The one persisted authority profile for project sessions on local and TRAMP targets. It uses a renewable `.lease/` and immutable publication head, never a client PID lock, and every mutation selects it from the session profile.
- **file-session authority** — The `pid-lock` profile reserved for non-project file workspaces. It uses `.lock` and has no portable lease/publication tree, but persists and fences the execution-target incarnation before mutation.
- **target incarnation** — A stable fingerprint of the execution target's boot or container lifetime. Portable project sessions persist it and compare a fresh local or TRAMP observation before reusing grants or mutation authority; both paths use one canonical payload.
- **physical control root** — A session lease, transfer, or recovery control directory opened and operated through a target-side pinned descriptor. One target process opens the directory, proves the opened directory is the requested physical path, and then works only through that descriptor, so pathname swaps cannot redirect authority.
- **target control time** — The target filesystem clock used for portable lease expiry and transfer deadlines, at whole-second resolution. Client wall-clock values cannot change portable authority.
- **unsettled target mutation** — Durable session safety state meaning a target mutation began but all of its target effects have not yet been proved settled. It remains through client loss and takeover until proof or explicit acknowledgement.
- **pending publication** — A locally retained completed turn whose durability-critical state has not yet reached the session's authoritative store. It blocks the next turn until publication succeeds or the user explicitly abandons recovery. _Avoid_: saved turn, unsaved draft
- **browser collaboration room** — One process-local, read-only browser projection of a live session's canonical visible transcript. The originating Emacs session remains authoritative; the room grants observation only and ends with the session, buffer, explicit stop, or Emacs process.
- **collaboration bearer link** — The room URL whose fragment contains the opaque room credential. Anyone holding it may read the projected content, which can contain credentials or secrets; without a configured operator-managed HTTPS origin it is loopback-only.
- **side conversation** — A transient, multi-turn conversation created from an immutable snapshot of a parent session's effective model-visible context. It may start during an active parent turn, inheriting only material complete at that moment, and then proceeds independently without synchronizing with or merging into its parent. Read-only inspection needs no extra approval, while every durable workspace effect requires one-shot user approval and remains shared after the side transcript is discarded.
- **patch proposal** — One model-proposed, ordered set of Add, Update, Delete, and Move filesystem changes submitted as a single tool call. It is inert until permission and patch review settle it.
- **patch review** — The staged user interaction for a patch proposal. It permits per-change selection, editing, and feedback, then atomically applies the selected subset or requests revision without writing files.
- **session fork** — A child session that continues from a selected assistant response in another session. Its inherited conversation history ends at that fork point; its permission mode, sandbox mode, session permission rules, resource grants, and other session settings are copied independently; and its live workflow ownership starts fresh.
- **rewind** — The in-place session undo operation that discards a selected model turn and everything later, then transactionally returns captured working-tree file contents to that turn's checkpoint. Snapshot coverage is limited to state mevedel captured, but an approved Rewind is not partially applied. It creates no session fork or redo variant and does not restore Git index or repository history. _Avoid_: restore
- **turn checkpoint** — The durable pre-turn session and captured-file state from which Rewind can discard that model turn and everything later. Every accepted model turn owns one, including the first turn; user-authored workspace directives are reconciled rather than replaced from the checkpoint. _Avoid_: rewind point, fork point
- **conversation fork** — A session fork created in the source session's current working directory without restoring historical file state. Each variant thereafter owns its directory setting independently; file changes are shared only while their current directories still refer to the same files.
- **worktree fork** — A session fork created with a new Git linked worktree where mevedel restores captured source-repository file state from the fork point on a best-effort basis. Files outside that repository remain shared and are not restored. The term records the fork's origin even if missing-directory recovery later retargets the session.
- **source session** — The immediate parent session of a session fork at one fork point. A source session may itself be a session fork elsewhere. _Avoid_: original session
- **fork point** — The successfully settled assistant response through which a session fork and its source session share conversation history. Streaming, aborted, and failed responses are not fork points.
- **fork point identity** — The stable identity of one successfully settled assistant response used to relate conversation variants independently of mutable turn numbering.
- **armed session fork** — A transient choice of fork point and fork type awaiting the next accepted child prompt. No child session, worktree, transcript mutation, or file restoration exists while it is armed.
- **conversation variant** — The source session or one of its direct session forks at one fork point. Variant sets are star-shaped: additional alternatives at that point are created from Source, not by re-forking a child. _Avoid_: conversation branch
- **detached session fork** — A surviving session fork whose source session no longer contains its fork point, commonly because Source was rewound or deleted. It retains its own history and may still relate to surviving sibling Forks, but cannot switch to the missing Source.
- **fork context disclosure** — A durable child-session record, visible to both user and model, that identifies the fork type, working directory, and historical-file restoration semantics.
- **live session epoch** — One continuous activation of a root session between `SessionStart` and `SessionEnd`. A persisted session may have multiple live epochs across resume; rewind, clear, and compaction begin context epochs within the same live epoch.
- **session setting** — Configuration owned by one session, initially derived from global defaults, preserved across resume, and copied when the session is forked without affecting other sessions.
- **session cockpit** — The central user-facing control surface for one session, presenting live session state and routing common workflow, configuration, and inspection actions.
- **tabulated cockpit surface** — A session-owned cockpit buffer for inspecting and acting on selectable resources in a table. Its header line carries identity, scope, and state; the keys themselves live in its help.
- **cockpit info panel** — A read-only buffer of aligned label/value rows holding a cockpit surface's complete state, opened with `i` from the surface that owns it. It keeps reports that can grow out of menu headers.
- **cockpit alert line** — The second cockpit header line, shown only when session state is off-nominal and naming just the conditions the user may want to act on.
- **permissions cockpit** — The tabulated cockpit surface listing remembered session and workspace authority, where one row can be revoked without affecting the others.
- **worktree cockpit surface** — The session cockpit surface for Git worktree status and actions, split between a transient status menu and an optional tabulated worktree list.
- **worktree session** — A session whose working directory is a Git linked worktree while still belonging to the same mevedel workspace.
- **instruction** — A user-authored, source-linked record that gives mevedel context or work to perform. An attached instruction is presented by an overlay, but the overlay is not necessarily the record's identity.
- **reference** — A source-bound instruction that contributes context without asking the agent to act. It owns no activity or recovery entry point and disappears when its entire source anchor or file disappears.
- **reference mention binding** — The association between a direct `@ref:N` mention and the exact selected reference. It follows that reference's latest state, but never a later reference that reuses its displayed number.
- **reference query mention** — An `@ref:{query}` mention that selects all currently matching references when dispatched rather than preserving an earlier result set.
- **file mention binding** — The association between an `@file` mention and the absolute pathname selected when the mention is bound. It follows the latest contents at that pathname rather than a file snapshot or filesystem object.
- **MCP mention binding** — The association between an `@mcp` mention and one server-name/resource-URI pair. It reads the resource's latest contents and treats a replacement server with the same name as the same locator.
- **agent mention** — An `@agent:name` mention that selects the currently registered agent definition by its unique name when dispatched.
- **directive** — A durable workspace-owned instruction that asks the agent to discuss or perform work. Once it has activity, it retains its identity when its source anchor becomes detached or its source file is missing and may be archived but not permanently removed.
- **directive anchor** — The directive's source association. It is attached while represented in a live source region, detached when that region disappears, and source-missing when the associated file is unavailable. _Avoid_: directive overlay
- **directive activity** — The workspace-owned planning, discussion, and implementation-attempt history of one directive. Exact activity material remains durable for follow-ups and inspection, while each model exchange also appears as a directive turn in its execution session's chronology.
- **directive turn** — A model turn initiated for one directive and shown in the shared execution-session view. It shares that session's operational and Rewind chronology but neither consumes nor contributes ordinary-chat conversational context. _Avoid_: directive event
- **directive discussion** — A read-only conversation owned by one directive and continued through directive turns using only that directive's durable history. Its capability ceiling forbids direct and delegated mutation; it may inform a later implementation without becoming ordinary-chat context.
- **directive composer scope** — The explicit, sticky selection that makes the shared session composer submit follow-ups for one directive instead of ordinary chat. Leaving it restores the ordinary-chat draft; accepting or cancelling directive planning leaves it automatically, and session resume starts in ordinary chat scope. _Avoid_: directive composer
- **directive inspector** — The explicit read-only presentation of a directive's durable request, planning, discussions, attempts, patches, settings, and recovery actions when its transcript turns or source presentation are unavailable. It replaces the displayed session view and owns no composer or live request. _Avoid_: directive activity surface, directive chat
- **directive execution session** — The session selected by a directive's first model request and reused for its later discussion and implementation attempts. A closed persisted session resumes on demand; an unavailable session requires explicit warned rebinding, and historical checkpoint links do not migrate. The workspace still owns the directive and its activity; the execution session owns chronological ordering and turn checkpoints.
- **archived directive** — A directive with activity whose source presentation and active-list entry are hidden while its activity and checkpoint links remain inspectable and restorable. _Avoid_: deleted directive
- **directive request** — The directive's current user-authored intent. Editing it after activity exists returns the directive to Ready for future work, while each earlier attempt retains the exact request it used.
- **directive plan** — A record-owned plan created for one directive whose acceptance starts one direct implementation attempt in that directive's existing execution session and working directory. The attempt receives and retains the exact accepted plan, approval selections, and normal action-specific directive context, but not the planning transcript; no standalone plan artifact is created.
- **proposed directive plan** — The current directive-plan candidate awaiting a user's decision after queued planning turns have drained. It remains actionable across session resume until accepted, revised, or cancelled; earlier proposals are drafts.
- **directive plan selection** — The Mode, Model, Skills, and Instructions chosen for a proposed directive plan. The selection survives revisions and remains editable after a startup failure until the implementation request starts, but resets for the next implementation action.
- **accepted directive plan** — An immutable approved directive plan awaiting or attached to its implementation attempt. A startup failure or Rewind before its attempt leaves it retryable, but changing the directive request or its subdirectives demotes an unstarted plan to a draft; once the request starts, its terminal result settles the attempt.
- **directive planning** — A top-level directive's durable, initially disabled preference to require a fresh accepted directive plan before every future implementation attempt. Nested subdirectives share their parent's preference; source loss and archival preserve it, and changing it does not alter planning already in progress.
- **directive planning status** — The visible Planning, Plan Ready, or Plan Accepted phase layered over a directive's underlying lifecycle until an implementation attempt starts or planning is cancelled.
- **directive planning conversation** — A read-only conversation owned by one directive that starts from the exact action-specific implementation context and exclusively occupies its execution session against ordinary Plan or another directive workflow. Failed or aborted turns remain recoverable within it; acceptance begins the intended implementation attempt, while cancellation ends planning without creating an attempt and retains its history.
- **directive plan draft** — A saved, non-actionable directive plan retained from a cancelled or superseded directive planning conversation.
- **directive batch planning** — Sequential planning of planning-enabled directives when each reaches the front of a batch queue. Each directive owns and approves its own plan after earlier batch attempts have settled; cancellation skips only that item, while a recoverable failure pauses the queue. _Avoid_: batch plan
- **directive model** — The model and reasoning effort selected on a directive. It governs discussion, planning, and implementation without directive planning; when absent, planning uses the planning workload while other directive turns inherit the session, and a planned implementation instead uses its directive implementation model.
- **directive planning turn** — A model turn in a directive planning conversation, retained separately from directive discussion and implementation attempts. Queued planning follow-ups each create their own turn rather than steering one already in progress.
- **subdirective** — A directive nested inside another directive that contributes supplementary instructions to its topmost parent's request rather than owning independent activity. A successful parent implementation consumes its submitted subdirectives; failure or abort retains them, and Rewind before that success restores them. _Avoid_: child directive
- **directive implementation attempt** — One accepted, isolated, file-mutating request made from a directive. Success, failure, and abort all retain their exact submitted request, available answer or error, outcome, captured patch and capture completeness, and link to the executing session and turn checkpoint; a later attempt does not overwrite them.
- **directive implementation mode** — The permission mode selected when accepting a directive plan. It applies only to that implementation attempt; the directive execution session's mode is restored afterward.
- **directive implementation model** — The request-local model and reasoning effort selected when accepting a directive plan. Its initial value is captured from the directive execution session's normal model and it changes neither the session nor the directive planning model.
- **directive implementation skill** — A skill selected directly or mentioned in implementation instructions for one accepted directive implementation attempt. Duplicate selections collapse to one canonical source, which must remain available when that attempt is dispatched.
- **directive implementation instructions** — Free-form guidance selected when accepting a directive plan and supplied only to that implementation attempt. It may refine mechanics but cannot replace the directive's intended outcome or the accepted plan's constraints.
- **directive patch** — The captured filesystem diff owned by one directive implementation attempt. It is historical review and Request changes context, not authoritative repository state or an independent undo record; a shared patch buffer may display it but never owns it.
- **capture completeness** — An implementation attempt's statement of whether its patch covers every observed mutation path. `No filesystem changes`, `Captured changes`, and `Capture incomplete` distinguish a true empty result from known coverage gaps.
- **request changes** — A new directive implementation attempt informed by the immediately preceding attempt and its accepted directive plan, when present, plus explicit user feedback, newly added subdirectives, or both. Older activity remains inspectable but is not automatically supplied, and the current directive request remains unchanged. _Avoid_: revise
- **retry** — A new directive implementation attempt after failure or abort, informed by the preceding accepted directive plan when present, error, captured partial changes, and optional additional guidance. _Avoid_: retry with guidance
- **goal** — A durable user objective that drives automatic root turns until it is complete, genuinely blocked, budget-limited, or paused. Planning and independent review are separate workflows rather than Goal phases.
- **achievement criteria** — The observable conditions that prove a Goal has been achieved. They govern completion even when implementation reasonably differs from the accepted plan.
- **goal steering** — An ordinary user message sent while a Goal is active. It guides the conversation without amending the durable Goal; compaction may retain relevant outcomes or facts, but does not independently carry its original wording forward. _Avoid_: objective update, persistent instruction
- **same-turn steering** — A user message accepted while a root turn is active and delivered as a durable user transcript message at the next model interaction boundary without creating another turn. Each boundary accepts every steering message already pending in FIFO order; later messages wait for the following boundary. Pending steering keeps the turn open if it would otherwise finish and takes priority over queued follow-ups regardless of submission order; it neither aborts the turn nor becomes a separate follow-up. Steering left undelivered when its turn fails remains pending for user review rather than changing category. _Avoid_: immediate send, queued follow-up
- **queued follow-up** — A user message accepted while a root turn is active and held to start its own separate turn afterward. Follow-ups retain FIFO order with each other, one turn per submitted message, but yield to all same-turn steering. _Avoid_: same-turn steering
- **pending input** — An accepted user message awaiting delivery as either same-turn steering or a queued follow-up. _Avoid_: queued message
- **Pending Inputs cockpit** — The session surface for inspecting, editing, deleting, reordering, and recategorizing pending input. _Avoid_: queue editor
- **goal turn** — Any root model turn started while a Goal is active, whether initiated by user steering or automatic continuation. Goal control commands, compaction requests, and child-agent turns are not Goal turns.
- **active Goal context** — The current durable Goal contract supplied to every Goal turn: objective, accepted plan reference when present, lifecycle state, budget, and terminal-state rules. It is independent of conversation history and is not reconstructed by compaction.
- **plan** — An implementation-ready approach for a requested outcome at its natural level of detail, regardless of approval state. It may lead to implementation here or in a worktree using current, fresh, or summarized context, or it may seed a Goal, but belongs to none of those execution paths.
- **plan draft** — Saved, non-actionable plan text that may seed a later Plan-mode conversation.
- **proposed plan** — The single current plan candidate awaiting the user's decision in Plan mode. A later proposal supersedes it rather than creating another pending approval.
- **accepted plan** — An immutable, user-approved implementation handoff. When it seeds a Goal, its stated outcomes, constraints, and achievement criteria are binding unless a later Goal-objective edit amends them, while its implementation mechanics remain revisable.
- **accepted plan reference** — The stable link from a Goal to the immutable accepted plan owned by that Goal's target session.
- **plan implementation context** — The conversation context supplied with an accepted plan: `current` retains the planning transcript, `fresh` starts with setup context and the plan only, and `summary` starts fresh with a handoff context summary and the plan but no verbatim tail. Worktree implementation supports only `fresh` and `summary`; every valid context/location combination may run directly or as a Goal.
- **direct plan execution** — One ordinary implementation turn for an accepted plan, including normal tool-call cycles but no automatic continuation or plan-owned completion lifecycle. Use a Goal when completion must be pursued durably.
- **Plan mode** — A sticky planning conversation in which the user and model create or revise a plan before the user accepts it or explicitly leaves planning. It may use a planning-specific model policy independently of the session's implementation model. Direct file-editing capabilities and Eval are withheld, and Bash is limited to recognized read-only commands regardless of permission mode or allow rules; other tools follow ordinary session permissions. Plan mode is toggled independently of permission mode. A session cannot enter Plan while it owns an unfinished Goal.
- **plan template** — Outcome-first guidance organizing a plan around Goal, achievement criteria, approach, regression coverage, validation, and assumptions. Its headings are not a parser-enforced schema or approval checklist.
- **goal status** — The lifecycle state controlling whether a Goal may continue: active, paused, blocked, budget-limited, or complete. `blocked` is reserved for a genuine task-level impasse; provider, compaction, transport, and other runtime failures pause the Goal instead.
- **goal token budget** — An optional limit on model tokens consumed by Goal turns. It gates new turns but does not interrupt an already-running turn; context-summary requests and child-agent usage are outside the budget. Exhausting it stops automatic continuation without implying completion.
- **goal budget reminder** — A one-shot notice when Goal usage crosses 50%, 80%, or 100% of its token budget, or whenever the user adjusts that budget. It reports current usage and remaining capacity without changing the completion contract.
- **permission guardian** — An opt-in model-based Bash risk reviewer that annotates pending permission decisions without granting authority. It is advisory in `ask` and `edits`; in `full-auto`, only a valid deny recommendation vetoes, while unavailable review leaves the unattended path unchanged.
- **guardian request** — An isolated model request whose trusted system instructions define one guardian's review policy and may include scoped project configuration and environment context, while its user message contains only the untrusted evidence being reviewed. Project context cannot override guardian policy or authority. The request does not inherit the session's coding-assistant prompt, transcript, tools, memories, or skills.
- **model workload** — A named kind of model request, such as planning, exploration, verification, or summarization, whose model and reasoning effort can be configured by a preset.
- **context summary** — Model-generated conversation context retained for continuation or transferred as background for a focused task. Display labels, tool summaries, reports, and session metadata are not context summaries.
- **continuation context summary** — A context summary that replaces older history within the same ongoing conversation. It may retain unresolved work as actionable context and may incorporate an earlier continuation context summary.
- **handoff context summary** — A context summary that transfers task-relevant background into another workflow or conversation. Its source material is evidence rather than an assignment; the separately supplied task remains authoritative.
- **conversation compaction** — Replacement of older model-visible transcript history with an anchored summary and a recent verbatim tail while retaining the original transcript on disk.
- **compaction attempt** — One bounded attempt to produce and apply a compacted context. It emits `PreCompact`; successful application emits `PostCompact`, and only a root-session success begins a `SessionStart(compact)` context epoch. A retry is a new attempt.
- **compaction target** — A model-visible transcript whose context pressure is managed independently through conversation compaction; currently either a main session segment or a persisted sub-agent transcript.
- **view buffer** — The compact, user-facing mevedel buffer with status, interaction, and input zones.
- **view disclosure** — A collapsible view-buffer element consisting of a visible disclosure header and an optional expanded disclosure body. Avoid “handler,” which refers to executable tool behavior.
- **status strip** — The mevedel-owned clickable header-line chrome in a view buffer that routes status items to session cockpit surfaces.
- **data buffer** — The authoritative gptel/org transcript buffer backing a view buffer.
- **agent transcript view** — A read-only projection of a sub-agent transcript,
  backed by the live agent while it is running and by its saved transcript after
  it reaches a terminal state. It is an observation-only view-buffer variant,
  not a separate transcript presentation or interaction surface.
- **tool** — A model-callable operation routed through mevedel's validation, permission, execution, rendering, and persistence pipeline.
- **tool attempt** — One validated model tool call passing through pre-use and permission gates. It receives one post-use outcome only when its handler runs; a model retry is a separate attempt.
- **permission-denied hook** — The `PermissionDenied` hook emitted exactly once after any final denial of a valid tool attempt, including rejection by `PreToolUse`. Its payload preserves the event that originated the denial.
- **permission-request hook** — The `PermissionRequest` hook emitted once when any tool's permission resolution produces `ask`, before the request enters the shared permission queue. Tool-specific cards, display, and queue re-evaluation do not create additional events.
- **tool input repair** — A deterministic correction to a tool call that either responds to a specific contract violation or is explicitly requested by the tool. Ordinary default values are tool semantics, not repairs.
- **permission rule** — A rule deciding whether a tool call is allowed, denied, or requires user approval.
- **permission mode** — A session setting selecting the autonomy ceiling `ask`, `edits`, or `full-auto`. It is independent of resource authorization and execution confinement; the same canonical names are used in user and system interfaces.
- **ask permission mode** — The permission mode that automatically authorizes recognized inspection while requiring user judgment for native edits, model-generated Eval, uncertain Bash, and other mutation unless a permission rule settles the operation.
- **edits permission mode** — The permission mode that automatically authorizes native file and directory edits and applies their previews after resource checks. Bash, Eval, and unrelated mutating tools retain `ask` behavior unless a permission rule settles them.
- **full-auto permission mode** — The permission mode that skips prompts caused only by heuristic uncertainty, including destructive writes inside authorized workspace roots and unprompted live Eval, and grants model-requested additive network access. Explicit denies and other prompts for authority not already granted survive, but live Eval remains inherently unconfined inside Emacs.
- **user-authoritative permission rule** — A durable-session, workspace-persistent, or global user rule that records direct user authority before permission-mode fallback: deny blocks, ask prompts even in `full-auto`, and allow settles the named operation without heuristic prompts or guardian review. A session-scoped rule survives save/resume of that session but does not enter unrelated sessions. Once independent resource authority is also satisfied, no catastrophic-command floor remains.
- **reusable Bash allow** — A user-authoritative permission rule created from an approval prompt only when the command source can be stored literally without wildcard or dynamic-shell ambiguity. Commands that cannot be represented that narrowly remain eligible only for invocation-scoped approval.
- **delegated permission rule** — An invocation- or request-scoped rule contributed by a skill or other delegated workflow. It may settle ordinary operations but cannot authorize dangerous or complex Bash, protected resources, or full execution escalation.
- **allowed root** — A directory whose files mevedel tools may access without crossing the workspace permission prompt. A session may extend its allowed roots through an explicit user grant.
- **recognized read-only Bash command** — A Bash invocation whose supported shell structure and command-specific argument policy identify no intended mutation. It is eligible for automatic execution only when identified file operands stay within allowed roots; the classification is not a general safety or confidentiality guarantee.
- **yielded Bash execution** — A Bash command that remains live and addressable after its initiating Bash tool call returns, until it stops or its execution owner or session ends.
- **execution ID** — The session-scoped opaque handle for a managed Bash execution. Models receive it only after yield; session-wide user controls may use it while the execution is still foreground. It is neither a chat session identifier nor an operating-system process identifier.
- **execution owner** — The main session agent or canonical sub-agent that started a yielded Bash execution and alone may address it through model tools. User-facing session controls retain authority over every execution in the session.
- **execution cockpit** — The session-owned table of every live managed Bash execution, including foreground work, with user-authoritative inspection, PTY input, interrupt, and stop controls.
- **execution output artifact** — The session-owned file containing the complete merged output of a yielded or oversized Bash execution when the displayed result is only a preview.
- **execution outcome** — The canonical interpretation of a Bash exit: `success`, `failure`, `no-match`, `different`, or `false`. It does not replace or rewrite the raw exit code or command output.
- **Bash command authorization** — The decision that a Bash invocation form may execute, established by an explicit permission rule or conservative command classification. An explicit allow rule may override any classifier category.
- **Bash resource authorization** — The separate decision that a Bash invocation may access its identified filesystem operands. It is cumulative with Bash command authorization, so allowing a command form does not grant paths outside allowed roots.
- **execution confinement** — OS-enforced restrictions applied to model-triggered child processes after permission authorization. It limits process effects but does not decide whether a tool call is allowed.
- **external tool helper** — A short-lived OS process launched by a native model-callable tool to implement part of that tool, such as searching files or converting media. It runs through the shared execution-confinement layer with tool-declared read paths and writable artifact directories.
- **sandbox mode** — A persisted session setting selecting whether execution confinement is `best-effort`, `required`, or `off`, initially copied from the global `best-effort` default. In `best-effort`, unavailable confinement falls back to disclosed direct execution without another prompt only when the requested command could not have started.
- **execution escalation** — A new model-requested tool invocation asking for an additional confinement capability after the default invocation failed or was refused. Mevedel explains how to retry but never creates an escalation prompt or replays the process automatically.
- **additional permission** — A network or path-specific read/write capability added to one confined Bash or batch Eval invocation through `with_additional_permissions`. It widens only the named capability and does not disable other confinement.
- **execution permission profile** — Additive network and exact filesystem requirements remembered on a user-authoritative Bash or batch-Eval rule. A later matching default invocation receives the union of direct profiles; an exact path is attached only while a sufficient resource grant also exists. Delegated rules never contribute profiles.
- **full execution escalation** — A `require_escalated` Bash or batch Eval invocation that bypasses child-process confinement because its requirement cannot be represented with additive permissions. It asks in every permission mode unless explicitly granted; session or workspace remembering is offered only when the operation can be stored literally without wildcard or dynamic ambiguity.
- **escalation rule qualifier** — The optional `:sandbox-permissions` condition on a permission rule. It does not cause escalation; it lets the rule match a tool invocation that already requests that execution level. Only user-authored rules may use it to grant full execution escalation.
- **protected path** — A user-configured path whose identified access requires confirmation or a covering explicit resource grant, and whose child-process confinement defaults to inaccessible. Project `.git` is the built-in exception: it defaults to read-only so inspection remains possible.
- **resource grant** — User authority for a specific filesystem path and access mode, scoped to one invocation, a durable session, or the workspace permission store. Session scope survives save/resume of that session but does not enter unrelated sessions. Write includes read and promotes an existing read grant rather than duplicating it; the grant never authorizes a Bash command form.
- **protected-path confinement mode** — The `read-only` or `inaccessible` value paired with a protected-path glob. A confinement compiler resolves it into concrete sandbox restrictions; it is not a literal mount instruction.
- **protected creation target** — A determinable protected directory root that does not yet exist beneath a writable parent. The confinement backend prevents its creation until the invocation receives an additive write permission.
- **confinement carve-out** — A path-specific read-only or inaccessible restriction applied after broader mounts so it survives an enclosing writable root. An approved invocation may receive a narrower additive read or write exception without disabling the rest of the sandbox.
- **mention binding** — The association created when a mention's exact target first becomes known. A bound mention never falls back to a same-named target, editing its visible token removes the association, and an unavailable target becomes an explicit annotation in the temporary request without blocking the turn or changing the stored user text.
- **malformed mention binding** — A binding whose stored shape or visible token is inconsistent, so its intended target cannot be trusted. It blocks live submission or causes persisted history to be quarantined rather than being reinterpreted as an unbound mention.
- **unbound mention** — A mention whose exact target is not yet known. It remains eligible for live resolution rather than preserving a missing-target result.
- **skill** — A reusable prompt package discovered from configured skill directories and invoked by `$skill` syntax or model-side `Skill` tool.
- **skill invocation role** — The interpretation of one skill use as either an instruction or a command. The invocation surface determines the role; the skill does not declare it.
- **skill instruction invocation** — An embedded `$skill` mention that contributes a prepared skill body to the current consumer without invocation arguments or changes to the consumer's request policy.
- **skill command invocation** — A leading `$skill` invocation or model-side `Skill` call that supplies arguments and runs according to the skill's execution context.
- **skill execution context** — The location in which a skill command runs: `inline` in the current session context or `fork` in a dedicated sub-agent.
- **skill mention binding** — The association between one user-written `$skill` token and the exact discovered skill source it names, independent of later same-name lookup.
- **skill policy override** — Session-preset model and reasoning-effort policy applied to an existing skill invocation without changing or duplicating the skill.
- **skill roster** — The model-facing list of active skill names and descriptions, including only enough metadata for the model to decide whether to invoke a skill.
- **skill lookup** — A model-facing search over enabled model-invocable skills, including dormant path-scoped skills that are not present in the active skill roster.
- **plugin** — A reusable extension bundle discovered from a plugin manifest. A plugin may contribute skills, hooks, and other implemented extension components.
- **plugin activation** — A workspace-scoped decision that makes a plugin's implemented components active for sessions in that workspace until disabled.
- **pending plugin hook consent** — A plugin activation state where plugin skills may remain active, but executable plugin hooks are withheld until the user reviews and approves the changed hook surface.
- **hook audit record** — Persisted structured metadata or transcript markup describing how a hook changed model-visible context, submitted content, control flow, or permissions.
- **hook audit surface** — The user-facing record that a hook changed model-visible context, control flow, permissions, or submitted content.
- **start hook** — A lifecycle hook marking entry into a new identity or context epoch, never merely another model request. `SessionStart` covers startup, fork, resume, rewind, clear, and compact epochs; `SubagentStart` covers creation of a retained agent and its conversation. _Avoid_: request start hook
- **session-start context** — An append-only snapshot of context contributed when a session enters or re-enters an active epoch. Resume adds a current snapshot without rewriting or deduplicating historical hook context.
- **sub-agent stop hook** — The `SubagentStop` lifecycle hook emitted whenever one agent turn settles. It does not end the retained agent or its conversation. _Avoid_: agent end hook
- **prompt submission hook** — The `UserPromptSubmit` hook emitted once for each root or retained-agent task input. Mailbox delivery and internal requests such as compaction, guardians, and automatic continuations are not prompt submissions.
- **pending hook context** — Model context produced when no request is sent, retained by the originating root or agent conversation and consumed exactly once by its next accepted task input. It never crosses between agents or into the root session.
- **prompt expansion hook** — The `UserPromptExpansion` hook emitted once per canonical skill actually prepared from a user `$skill` invocation. Repeated mentions of the same skill and model-side `Skill` calls do not create additional expansion events.
- **hook context composition** — The non-recursive ordering that runs start hooks, user skill expansion hooks, and the prompt submission hook before merging their context once into model input. Hook output is never reinterpreted as another skill invocation or rerun through earlier hooks.
- **turn terminal hook** — The single observational hook emitted when a turn settles: `Stop` for root success, `StopFailure` for root error or abort, and `SubagentStop` for any settled agent turn. It cannot reject settlement or continue the turn.
- **plugin cockpit** — A session cockpit surface for inspecting installed plugins and managing one selected plugin at a time.
- **agent** — A delegated model participant whose identity is distinct from any one unit of work it performs.
- **agent conversation** — The context retained by one agent across its turns. Follow-ups continue it; spawning another agent starts a fresh conversation.
- **agent context selection** — The context chosen when creating a child agent: isolated, task-focused summary, complete parent context, or a positive number of recent parent turns. Any parent material is frozen at selection time and later parent turns are not synchronized into the child. _Avoid_: agent context fork
- **agent task background** — A task-focused handoff context summary persisted as advisory child conversation context immediately before the authoritative Agent Task. It is neither a replayed parent turn nor a child assignment.
- **agent model policy** — The model and reasoning effort resolved for an agent from parent defaults, then role or workload policy, then optional explicit Agent overrides.
- **agent task name** — The caller-supplied local name of a child agent, restricted to lowercase ASCII letters, digits, and underscores.
- **agent path** — The stable model- and user-facing address formed by joining an agent's task name to its parent's path, such as `/root/spec_review`. It is distinct from the opaque storage identity.
- **relative agent path** — A model-facing descendant address resolved beneath the caller's canonical path. Cross-branch or ancestor targets use canonical paths instead.
- **agent roster** — The tree-wide, path-sorted list of retained agents exposed by ListAgents, with each agent's path, role, and current activity status.
- **agent registry** — The explicitly persisted root-session index of addressable agent identities, paths, topology, configuration snapshots, activity, mailboxes, and conversation storage.
- **historical agent transcript** — A read-only child transcript retained for inspection without registering an addressable agent identity, such as an artifact copied into a session fork.
- **agent role** — An optional named configuration overlay that specializes an agent's instructions, tools, or model policy without defining a different runtime kind. _Avoid_: agent type, subagent type
- **agent configuration snapshot** — The role, instructions, tools, base model, effort, and inherited configuration resolved at spawn and retained unchanged across follow-ups and resume.
- **agent permission origin** — The canonical agent path attached to a root-session permission-queue entry so one shared human authority surface can attribute and settle requests from the whole tree.
- **agent-tree authority** — The root session's permission mode, sandbox mode, user-authoritative permission rules, and resource grants shared by every agent in its tree. A child agent may exercise existing authority but cannot raise it; unresolved authority requests enter the root session's permission queue with the requesting agent's canonical path.
- **default agent role** — The role used when delegation names no specialization; it inherits the delegating agent's effective configuration and capabilities.
- **worker agent role** — A built-in implementation overlay with broad direct tools, explicit file ownership guidance, concurrent-edit coordination, and delegation authority. It has no distinct runtime semantics and does not inherit a read-only delegator's tool ceiling.
- **agent turn** — One bounded unit of work performed by an agent. Every agent turn executes asynchronously, whether or not its owning workflow waits for the result.
- **active agent turn** — An agent turn that has started but not settled, including while it waits for child work. Active agent turns consume the shared capacity of their session tree.
- **settled agent** — An addressable agent with no active turn. It retains its conversation for the lifetime of the root session but consumes no agent-turn capacity.
- **agent-turn capacity** — The maximum number of active non-root agent turns permitted across one session tree. Agent identities, tree depth, and settled turns do not consume it.
- **awaited agent turn** — An agent turn whose owning workflow delays completion until the result settles. _Avoid_: foreground agent, background agent
- **agent wait** — An explicit, event-driven wait for the first queued or newly arriving mailbox activity from any agent in the root session tree. New user input interrupts it; otherwise the caller's turn remains active and consumes agent-turn capacity during the wait.
- **agent wait timeout** — A successful WaitAgent outcome when no activity arrives before its bounded deadline; it does not imply failure or terminate any agent.
- **parent agent** — The agent or root session that directly created an agent and owns their communication relationship.
- **agent result owner** — The spawn parent that receives one automatic queue-only result for every settled turn of its child, regardless of which agent initiated a later follow-up.
- **agent result** — A RESULT mailbox record sent to the spawn parent when a child turn settles, carrying canonical sender and recipient paths, the completed, errored, or interrupted outcome, and its plain-text payload.
- **child agent** — An agent directly created by one parent agent.
- **agent delegation** — Creation of a child agent by any agent whose capabilities include the Agent tool. Delegation is not reserved for the root session or a coordinator role.
- **delegation authority** — The transitive ability conferred by the Agent tool to create any agent role available to the session. Default, worker, and explorer have Agent and WaitAgent; reviewer, verifier, and custom roles that omit Agent remain leaves. A role's direct tool restrictions do not restrict its descendants; session permissions remain the outer authority boundary.
- **agent control tools** — Agent, FollowupAgent, WaitAgent, and InterruptAgent. They are bundled for roles with delegation authority; passive SendMessage and ListAgents remain available to every role.
- **agent message** — Queue-only information sent directly between any two addressable agents in the same root session tree.
- **agent mailbox** — The persisted per-agent FIFO of unread communication records waiting to be injected separately into that agent's conversation before a model sample. Injected records leave the FIFO and remain in conversation history. WaitAgent observes mailbox activity but does not return mailbox content.
- **agent follow-up** — A task sent to an existing non-root agent that continues its retained conversation and ensures it receives an agent turn. Unlike an agent message, it starts a turn when the target is idle; agents cannot start the root session.
- **agent interruption** — Cancellation of one non-root agent's current turn without affecting its descendants, retained conversation, canonical path, or future follow-ups. It does not remove the agent.
- **task** — A tracked work item within a Goal or ordinary session work, optionally with dependency links.
- **persistent memory** — Durable user- or workspace-local memory included in future sessions.
- **ADR** — An architecture decision record under `docs/adr/` for durable decisions that should constrain future design work.

- If a term is missing or ambiguous, ask or use `$grill-with-docs` to resolve it before adding competing vocabulary.
